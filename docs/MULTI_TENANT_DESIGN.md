# Multi-tenant design: one deployment, many clients

**Status:** proposal. Docs only — no code, no migration, no schema applied.
Every file:line below was read in this repo on 2026-11-09 at `origin/main`
(`de2c8fe`).

The goal: one deployment serves every client. The layout stays identical; only
client data and page content change. Assets (logo, photos, video) must not ship
inside the deployment. The owner edits content with one agent command, not a page
builder.

Two facts worth stating plainly:

- **The per-client config path already exists.** `build-static.js --config` merges a
  JSON file over `BIZ` (`build-static.js:72-76`) and warns on unknown keys. What is
  missing is not the idea of a config, it is where the config lives and when it is
  read. Today it is a file and it is read at build time.
- **The token fill is implemented twice** — once in `build-static.js`, once in the
  runtime IIFE (`index.html:2639`). A third implementation for server rendering
  would be the one that drifts. Extract it first.

## 2. Data model (proposal — SQL text only, not applied)

Three tables. `businesses`, `business_chats`, `leads`, `lead_events`,
`review_feedback` are untouched, so the bot and the email code keep working
exactly as they do now.

```sql
-- One row per client site. The business row stays the source of truth for
-- phones, leads and review links; this table is the website.
create table public.sites (
  id              uuid primary key default gen_random_uuid(),
  business_id     uuid not null references public.businesses(id) on delete restrict,
  slug            text not null unique,
  template        text not null default 'roofer-v1',
  site_url        text not null,                -- https://www.example.com, no trailing slash
  status          text not null default 'draft'
                    check (status in ('draft', 'live', 'paused')),
  noindex         boolean not null default true,
  content         jsonb not null default '{}'::jsonb,
  content_version integer not null default 1,
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now()
);
create index sites_business_idx on public.sites (business_id);

-- host -> site. Store the apex and the www form as two rows; do not fold them
-- in code, because a client may want only one of the two.
create table public.site_domains (
  host        text primary key,                 -- lower-case, no scheme, no path
  site_id     uuid not null references public.sites(id) on delete cascade,
  is_primary  boolean not null default false,
  verified_at timestamptz,
  created_at  timestamptz not null default now()
);
create unique index site_domains_one_primary
  on public.site_domains (site_id) where is_primary;

-- Asset references. The bytes live in object storage; this table is the index
-- and the only place a path is allowed to appear.
create table public.site_assets (
  id           uuid primary key default gen_random_uuid(),
  site_id      uuid not null references public.sites(id) on delete cascade,
  kind         text not null check (kind in ('logo','photo','video','poster','og')),
  storage_path text not null,                   -- bucket key, never a full URL
  mime         text,
  width        integer,
  height       integer,
  bytes        bigint,
  alt          text,
  created_at   timestamptz not null default now(),
  unique (site_id, storage_path)
);

alter table public.sites        enable row level security;
alter table public.site_domains enable row level security;
alter table public.site_assets  enable row level security;

revoke all on public.sites        from anon, authenticated;
revoke all on public.site_domains from anon, authenticated;
revoke all on public.site_assets  from anon, authenticated;
```

**Posture matches production**: RLS on, zero policies, no `anon`/`authenticated`
table grants. Every read goes through `service_role` in `api/`, exactly like
`lib/db.js` does today. The public never queries these tables directly; the
renderer is the only reader.

**Domain → business.** `host` → `site_domains.site_id` → `sites.business_id` →
`businesses.id`. The bot resolves a chat to `business_chats.business_id` and never
touches `sites`, so nothing in `api/tg.js` changes. The email code resolves
`businesses.owner_email` the same way; only the brand/logo lookup becomes
site-aware.

**Why not put the content on `businesses`?** Because a business can exist without a
site (a phone-only client), and because `businesses` is read by the alert path on
every lead — adding a large `jsonb` column to it puts the website's payload on the
hot path of the alert.

## 3. Content schema

One JSON Schema per template version, stored in the repo at
`lib/content-schema/roofer-v1.json`, validated by the publish command and by a
test. Draft 2020-12.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "roofer-v1",
  "type": "object",
  "required": ["hero", "services", "faqs", "seo"],
  "additionalProperties": false,
  "properties": {
    "hero": {
      "type": "object",
      "required": ["headline"],
      "additionalProperties": false,
      "properties": {
        "headline": { "type": "string", "minLength": 8, "maxLength": 120 },
        "sub":      { "type": "string", "maxLength": 240 },
        "cta":      { "type": "string", "maxLength": 40 },
        "video":    { "$ref": "#/$defs/media" },
        "poster":   { "$ref": "#/$defs/media" }
      }
    },
    "stats": {
      "type": "array", "maxItems": 4,
      "items": {
        "type": "object", "required": ["value", "label"], "additionalProperties": false,
        "properties": { "value": { "type": "string" }, "label": { "type": "string" } }
      }
    },
    "about": {
      "type": "object", "additionalProperties": false,
      "properties": {
        "heading": { "type": "string" },
        "body":    { "type": "string", "maxLength": 1200 },
        "photo":   { "$ref": "#/$defs/media" }
      }
    },
    "services": {
      "type": "array", "minItems": 3, "maxItems": 8,
      "items": {
        "type": "object", "required": ["title", "body"], "additionalProperties": false,
        "properties": {
          "title": { "type": "string", "maxLength": 60 },
          "body":  { "type": "string", "maxLength": 320 },
          "icon":  { "type": "string", "enum": ["replace", "storm", "repair", "inspection", "gutter", "flat"] }
        }
      }
    },
    "steps": {
      "type": "array", "maxItems": 5,
      "items": {
        "type": "object", "required": ["title", "body"], "additionalProperties": false,
        "properties": { "title": { "type": "string" }, "body": { "type": "string" } }
      }
    },
    "gallery": {
      "type": "array", "maxItems": 8,
      "items": {
        "type": "object", "required": ["before", "after"], "additionalProperties": false,
        "properties": {
          "before": { "$ref": "#/$defs/media" },
          "after":  { "$ref": "#/$defs/media" },
          "caption": { "type": "string", "maxLength": 120 }
        }
      }
    },
    "faqs": {
      "type": "array", "minItems": 3, "maxItems": 12,
      "items": {
        "type": "object", "required": ["q", "a"], "additionalProperties": false,
        "properties": { "q": { "type": "string", "maxLength": 160 }, "a": { "type": "string", "maxLength": 800 } }
      }
    },
    "seo": {
      "type": "object", "required": ["title", "description"], "additionalProperties": false,
      "properties": {
        "title":       { "type": "string", "minLength": 10, "maxLength": 60 },
        "description": { "type": "string", "minLength": 50, "maxLength": 160 },
        "keywords":    { "type": "array", "maxItems": 12, "items": { "type": "string" } },
        "twitter":     { "type": "string", "pattern": "^$|^@[A-Za-z0-9_]{1,15}$" },
        "ogImage":     { "$ref": "#/$defs/media" }
      }
    },
    "sections": {
      "type": "array",
      "description": "Order and visibility of the fixed sections. No new section types.",
      "items": { "enum": ["hero", "stats", "about", "services", "steps", "gallery", "reviews", "faqs", "cta"] },
      "uniqueItems": true
    }
  },
  "$defs": {
    "media": {
      "type": "object", "required": ["assetId"], "additionalProperties": false,
      "properties": {
        "assetId": { "type": "string", "format": "uuid" },
        "alt":     { "type": "string", "maxLength": 200 }
      }
    }
  }
}
```

**What the client can change:** every string in the schema, the service and FAQ
lists, the section order, which photos and video appear, and the SEO fields within
their length limits.

**What needs a template change:** a new section type, a new layout, a new icon
outside the enum, a different number of services than 3–8, a second video, or any
markup. That is deliberate: the layout is the product, and letting content invent
structure is how five client sites stop looking like one product.

## 4. Rendering: three options, one recommendation

| | (a) Client-side fill (today) | (b) Host-based server render | (c) Static build per client |
|---|---|---|---|
| **SEO: meta, canonical, JSON-LD, og** | Fails for link previews. Slack, Facebook, iMessage fetch raw HTML and run no JS; today `build-static.js` bakes the values at build time, which is why (a) only works with one client per build | Correct: the first byte carries the right tags | Correct |
| **Speed** | One HTML file, but the tokens are filled after parse | CDN-cached HTML, same as static when the cache hits; one function invocation per miss | Static, fastest possible |
| **Content edit without deploy** | Yes (DB read in the browser) — but the tags stay wrong | Yes | No: every edit is a build and a deployment |
| **Deployment size** | 1 × 125 MB | 1 × 125 MB (or ~15 MB once assets move to storage) | N × 125 MB |
| **Cost** | 1 project | 1 project + domains | N deployments per edit; this is what filled the 10 GB |
| **Migration effort** | none, but it cannot serve two clients | medium: one renderer, one shared token fill | low per client, high per edit |
| **Failure mode** | wrong preview card, wrong canonical | a cache miss costs ~200 ms | a stale page until someone deploys |

**Recommendation: (b), host-based server rendering of the existing HTML template,
with assets in object storage.**

The page is one 279 KB HTML file with inline CSS and three vendor scripts. A
function resolves `Host` → `sites` row → `content`, fills the same `{{tokens}}`
the build fills today, and returns the HTML with
`Cache-Control: public, s-maxage=300, stale-while-revalidate=86400`. The CDN serves
every repeat request; a content edit is visible within the s-maxage window and
never needs a deployment.

What it needs from the platform:

- **Many domains on one project.** Vercel supports multiple domains per project;
  the exact Hobby limit is not verified here (see §8).
- **The `Host` header inside the function.** Standard on Vercel functions; not
  verified on this project's plan.
- **CDN caching of a function response.** `s-maxage` + `stale-while-revalidate` is
  the mechanism; the project already relies on `Cache-Control` headers in
  `vercel.json:29-51`, so the header path is proven, the function-cache path is not.

**One implementation of the fill.** `build-static.js` and the runtime IIFE must
both call the same `lib/fill-template.js`. The runtime IIFE stays for `file://`
previews and becomes a no-op on a rendered page. This is the single most important
refactor before (b), because three copies of a token replacer is exactly how the
`//n` bug shipped.

**Unverified:** whether a 279 KB HTML response plus a Supabase round trip fits
comfortably in a Hobby function's cold-start budget. The number to measure is p95
first-byte on a cache miss, not the average.

## 5. Assets

**Where they live.** A Supabase Storage bucket, `site-assets`, public read, one
prefix per site:

```
site-assets/{site_id}/logo/logo-on-dark-{hash}.png
site-assets/{site_id}/logo/logo-on-light-{hash}.png
site-assets/{site_id}/photos/{name}-{hash}.avif
site-assets/{site_id}/video/hero-1080-{hash}.mp4
site-assets/{site_id}/video/hero-poster-{hash}.webp
```

Supabase is already the vendor, the service role key already exists, and the bucket
policy can be "public read, service-role write" without a second account. Cloudflare
R2 would be cheaper for egress and is the obvious move if bandwidth becomes the
bill; it is not worth a second vendor on day one.

**Limits, enforced at upload:** logo ≤ 200 KB (PNG or SVG, 2× and 1× rendered from
one master), photo ≤ 400 KB after the pipeline, hero video ≤ 8 MB (1080p, ≤ 12 s,
no audio), poster ≤ 250 KB, og image ≤ 300 KB (1200×630 JPEG).

**Pipeline.** `sharp` for images: one master in, AVIF + WebP at 3 widths out, plus
the 1200×630 crop for og. `ffmpeg` for video: H.264 1080 and 720 plus an AV1
variant, poster frame extracted at 1 s, audio stripped. Both are already in the
repo's dependency set (`sharp` in devDependencies; `ffmpeg` is external and must be
documented as a machine prerequisite).

**Emails.** The logo is attached as a CID image today (`lib/email-layout.js:76`,
`lib/mail.js:99`) from `assets/email/logo-on-dark.png`. In a multi-tenant world the
attachment is fetched from storage per send and cached in memory per process, keyed
by `site_id`. It must be resized to 32 px on upload, not on send: an email must not
depend on a network fetch at send time.

**What this fixes.** The deployment drops from ~125 MB to ~15 MB once the six hero
videos (110.9 MB) leave the repo. That is the same fix as the Vercel storage
problem, and it is a prerequisite for (b) being cheap.

## 6. Operations

### `npm run new-client -- --slug acme --name "Acme Roofing" --email owner@acme.com`

Creates, in one transaction where possible:

1. `businesses` row if the slug is new (status `demo`, timezone from `--tz`, review
   URL empty).
2. `sites` row: `status = 'draft'`, `noindex = true`, `content` seeded from
   `lib/content-schema/roofer-v1.default.json`.
3. Nothing else. No assets, no domain.

Prints: the site id, the draft preview host, and the three things a human must do
(next paragraph). Refuses if the slug exists, if the business is missing, or if the
content default does not validate.

### `npm run publish-client -- acme`

1. Validates `sites.content` against the schema for `sites.template`.
2. Checks every `assetId` in the content exists in `site_assets` and its object is
   present in the bucket.
3. Checks `site_url` is https and matches a `site_domains` row.
4. Sets `status = 'live'`, `noindex = false`, bumps `content_version`.
5. Prints the domain to point, the DNS record type and target, and the health URL.

Refuses on: schema failure (prints the JSON Pointer), a missing asset, a missing
domain row, or `noindex` still true while `status` is live.

**What stays manual, on purpose:** DNS (the owner controls the registrar), client
approval of the copy, and the first deploy of a new template version. The commands
never touch DNS and never deploy.

### Adding a domain

Dashboard → project → Domains → add, or `vercel domains add`. Then insert the
`site_domains` row with `verified_at` once the certificate is issued. The renderer
falls back to a 404 for an unknown host, so a domain added in DNS but missing from
the table shows nothing rather than the wrong client.

### noindex until go-live

`sites.noindex` drives both the `<meta name="robots">` tag and the
`X-Robots-Tag` header. The current global header (`vercel.json:86`) must be removed
when the first second client exists, or every client is noindexed forever. Until
then it is the belt to the per-site braces.

## 7. Migration plan

Each step is at most one PR. Effort is a rough estimate for one engineer who knows
this repo, not a promise.

| # | Step | Test plan | Effort | When |
|---|---|---|---|---|
| 1 | Move the six hero videos and the og image out of `assets/` into storage; reference by URL | build has no `.mp4`; page loads from a cold cache; `dist` < 20 MB | 1 day | before the first client |
| 2 | Extract `lib/fill-template.js`; `build-static.js` and the runtime IIFE both call it | golden build: output byte-identical for the same BIZ | 1 day | before the first client |
| 3 | Add `sites`, `site_domains`, `site_assets` + RLS migration | posture test (RLS on, zero anon grants) mirrors `db-wall` | 0.5 day | before the first client |
| 4 | Move the copy out of `index.html` into `content` JSON + schema; build reads content | schema tests, golden build with the same content | 2 days | before the first client |
| 5 | `new-client` / `publish-client` + validation | one test per refusal path | 1.5 days | before the first client |
| 6 | Host-based renderer behind a flag, one host, one site | two hosts, two contents, same HTML shell; cache headers asserted | 3 days | before client #2 |
| 7 | Per-site email logo and brand tokens at send time | email renders the right logo for two sites in one process | 1 day | before client #2 |
| 8 | Remove the global `X-Robots-Tag`, per-site noindex only | header test per host | 0.5 day | before client #2 |

**Before the first real client:** 1, 2, 3, 4, 5. That is a single-client system
with the content in the database and the assets out of the deployment — it already
solves the storage bill and the edit-without-deploy problem, and it can still be
built as one static deployment per client if the renderer slips.

**Can wait:** 6, 7, 8. They are what turn "one deployment per client" into "one
deployment for all clients", and they are only worth doing when there is a second
client to serve.

**Risks, honestly:**

- **SEO regression at cutover.** The current page is baked; a renderer that misses
  a token ships `{{name}}` to a crawler. The golden-build test in step 2 is the
  guard, and it must compare bytes, not substrings.
- **The token fill is the historical bug site.** `//n` shipped because a template
  was hand-edited. One shared implementation plus a test that every `{{token}}` in
  the template has a provider is the mitigation.
- **Hobby is not a commercial plan.** One client taking money needs Pro, which also
  changes the domain and function limits this design depends on.
- **Storage egress.** Moving 110 MB of video to object storage moves the bill from
  deployment storage to bandwidth. At one hero video per visitor it is small; at
  scale it is the line item to watch.
- **Schema churn.** Every new section type is a schema version and a template
  version. Clients on `roofer-v1` do not get `roofer-v2` for free; that is a
  migration per site, and it should be priced as one.

## 8. What is unverified

- The Hobby plan's domain limit per project, and whether a custom domain on Hobby
  can be added without a paid seat.
- Whether a Vercel function response can be cached at the edge with `s-maxage` on
  this plan the way a static file is; the header is in `vercel.json` today, but the
  function-cache path has not been exercised.
- The real p95 first-byte for a 279 KB rendered response plus one Supabase query.
- Supabase Storage's public-read bandwidth cost at this project's scale.
- Whether Vercel's Deployment Storage counts the uploaded source as well as the
  build output (see the `vercel-storage` PR). If it does, step 1 is worth double.
