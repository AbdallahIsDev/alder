### One coherent lead flow

1. `/leads` opens one message. Each lead button names the person, service, and age; no phone or email appears on the list.
2. Newer and Older stay in the same message. Render both ends disabled, with server-side handling that remains harmless if a client ignores `disabled`.
3. A lead button edits the message to a detail view with current status and the existing contact information. Mark contacted, Job completed, and review confirmation continue to re-read the row and apply conditional status transitions.
4. Back carries the list page token and restores that page. `/remove_lead` opens the same view in removal mode; selecting a lead opens a confirmation; Cancel returns to the same page; Confirm rechecks the row and tenant, deletes, then refreshes that page.
5. Start with a bounded page number in callback data. A 3-digit page plus action and UUID fits the 64-byte callback limit; still enforce it in a test. Re-fetch binding and row on every callback. Do not trust a callback's page or lead id for authorization.

**Deferred keyset paging (handoff item 5b):** keep offset paging for the current bounded workflow, but add an `id` tie-breaker to the `created_at` order before depending on stable page numbers. New rows can shift offset pages, and equal timestamps currently have no deterministic order. The existing `leads_business_created` index covers `(business_id, created_at desc)`; verify an index for `(business_id, created_at desc, id desc)` before moving to keyset paging. Keyset needs both directions and a cursor history so Back restores the same page. Prefer a short opaque cursor stored server-side over embedding timestamps and ids; bind cursor state to chat, message, and business. Keep item 5b deferred until lead volume or observed page drift justifies the schema/state cost.

## Rich Messages and no `parse_mode`

They are compatible if the bot uses the structured form. The saved reference defines `sendRichMessage` with required `rich_message: InputRichMessage`; `InputRichMessage` requires exactly one of `html`, `markdown`, or `blocks`. Choose `blocks: Array<InputRichBlock>` and typed `RichText` values. Do not use the `html` or `markdown` alternatives, and do not add `parse_mode`.

The received `RichMessage` has `blocks` and optional `is_rtl`. `sendRichMessage` can also take `reply_markup`. `RichMessageButton` supports `text: RichText`, `style`, `url`, `callback_data`, `web_app`, `login_url`, `switch_inline_query`, `switch_inline_query_current_chat`, `switch_inline_query_chosen_chat`, `copy_text`, and `disabled`. Its styles are `danger`, `success`, `primary`, and `link`; `link` is only for callback buttons. Standard `InlineKeyboardButton` has `text`, optional `icon_custom_emoji_id` and `style`, plus the action fields including `copy_text` and `disabled`. These are structured API fields, not `parse_mode`.

## Guardrails and open questions

- Keep tenant identity from `business_chats.tg_chat_id`; `business_chats.tg_chat_id` is unique. The operator chat is a separate private-chat role. Keep callback regexes anchored and every lead lookup/update/delete scoped by both `id` and `business_id`.
- Keep C40's no-`parse_mode` guarantee. When adding APIs, check all send and edit payloads, not only `sendMessage`; structured Rich Message support should not weaken the invariant.
- The saved docs do not state minimum Telegram client versions for `is_persistent`, `disabled`, `copy_text`, button styles, or Rich Messages. Verify iOS, Android, Desktop, and Web before exposing them broadly.
- If a Mini App is later justified, send `Telegram.WebApp.initData` to the backend, derive the HMAC-SHA-256 secret using the `WebAppData` key and bot token, compare the computed hash over the sorted data-check string, and check `auth_date`. The docs explicitly say not to trust `initDataUnsafe`.
- Product questions not answered by the saved docs: whether owners/operators prefer a persistent keyboard over the native command menu; expected lead volume and acceptable page drift; whether copying phone numbers is wanted; whether the product will ever collect digital payments or needs a Mini App.
